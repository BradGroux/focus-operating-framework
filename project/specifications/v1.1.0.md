# Focus Operating Framework v1.1.0 release specification

- **Status:** Accepted release specification
- **Owner and founding steward:** Brad Groux
- **Accepted:** 2026-08-22
- **Target release:** v1.1.0
- **Public proposal:** [Issue 6](https://github.com/BradGroux/focus-operating-framework/issues/6)
- **Product type:** Independent, documentation-only individual operating framework

## Purpose

This specification governs the v1.1.0 documentation release. It supplements
the immutable [v1.0.0 specification](v1.0.0.md) and does not revise the
requirements or evidence of that release.

## Release decision

Version 1.1.0 adopts Open Framework Commons v1.1.0 and records the Commons
decision recognizing Focus as an independent ecosystem product. This is a
backward-compatible minor release. The adoption decision is recorded in
[ADR 0009](../../docs/adr/0009-adopt-open-framework-commons-v1-1-0.md).

The exact adopted Commons release is:

- annotated tag: `v1.1.0`;
- tag object: `79e5f06dab46f262cad1d1daf7840e683ffc3880`;
- peeled commit: `f25a2b89b4aed95984fd235e2e229efe52c125d8`; and
- tree: `3216f7dc5dc0172df163bf50c13f57013a9125ff`.

## Required content changes

The release must:

1. update every current Commons adoption pin and compatibility statement;
2. state recognition without implying parent authority, inheritance, or loss of
   Focus independence;
3. preserve the definition, Mission, first job, ten commitments, six concerns,
   seven flexible moves, and all existing practice boundaries;
4. generalize release governance and review prompts for releases after v1.0.0;
5. add a machine-readable version and synchronized citation metadata;
6. add bounded issue and pull-request templates without adding CI or framework
   runtime behavior;
7. retain every v1.0.0 specification, pilot, review, disposition, tag, and
   release record unchanged; and
8. publish complete changelog and release documentation with evidence limits.

## Explicit non-changes

Version 1.1.0 does not change:

- the one-individual scope;
- work, personal, and combined life-scope choice;
- paper as a first-class complete path;
- selective foreground admission;
- provenance and record-of-authority distinctions;
- Transition Check-In, Reflection, Journal, and Journal Entry boundaries;
- Personal Mission Control as optional, derived, and non-authoritative;
- complete unassisted and optional AI-assisted paths;
- AI as source-backed, advisory, proposal- and draft-only, and unable to execute
  an external mutation;
- connector permission as distinct from action approval;
- defer, release, stop, no action, portable exit, and manual continuity; or
- the prohibition on effectiveness, safety, compliance, or outcome guarantees.

## Repository stewardship scope

The release may add issue and pull-request templates that improve proposal
quality and remind contributors of authority and public-hygiene boundaries.
Templates are repository-management surfaces, not framework doctrine.

The release must not add application code, schemas, provider-specific connector
designs, automation, CI, runtime behavior, technical conformance,
certification, or a required implementation.

## Review-record allowlist

Only these v1.1.0 generated review records may be added after the clean content
candidate is frozen and independently reviewed:

- `project/reviews/v1.1.0-practical-application-review.md`
- `project/reviews/v1.1.0-adversarial-misuse-review.md`
- `project/reviews/v1.1.0-canonical-coherence-review.md`
- `project/reviews/v1.1.0-accessibility-and-plain-language-review.md`
- `project/reviews/v1.1.0-public-hygiene-review.md`
- `project/reviews/v1.1.0-release-integrity-review.md`
- `project/reviews/v1.1.0-review-disposition.md`

No release-assembly or post-merge verification result enters the repository
tree.

## Verification gates

Before publication, the release must pass:

1. clean-tree, branch, remote, and authorship inspection;
2. local Markdown link and heading-target validation;
3. canonical commitment, concern, move, authority, AI, individual-scope, and
   Commons-pin comparison;
4. seven-example structure and illustrative-status validation;
5. public-hygiene and unsupported-claim inspection;
6. citation, license, changelog, version, and release-metadata consistency;
7. CFF 1.2 schema validation;
8. compilation of every tracked Mermaid diagram for visual inspection;
9. complete staged-diff secret scanning with redacted output;
10. six isolated independent reviews of an exact clean content candidate;
11. disposition of every finding, limitation, rerun, and material dissent;
12. release-assembly verification and detached attestation digest;
13. merge-tree identity with the verified final candidate;
14. immutable annotated tag and public release creation; and
15. authenticated public readback of identity, tree, tag, release, links,
    review records, attestation, and issue/PR dispositions.

Passing these gates establishes documentation and publication integrity only.
It does not prove real-world effectiveness.

## Release sequence

1. Freeze a clean content-candidate commit without v1.1.0 generated review
   records.
2. Run the six isolated independent reviews against that exact commit and tree.
3. Correct findings through a new candidate and affected reruns when required.
4. Add only final approved reports at the seven allowlisted paths.
5. Produce the complete review disposition.
6. Freeze and verify the final release candidate without changing its tree.
7. Merge through a pull request whose merged tree is byte-identical to the
   verified final candidate.
8. Create the immutable annotated `v1.1.0` tag carrying the detached attestation
   SHA-256.
9. Publish release metadata containing the byte-identical attestation.
10. Read every public surface back before claiming completion.
